🏗 1 · Architecture & Tech Stack | معماری و پشته‌ی فناوری

🧱 Tech Stack | پشته‌ی فناوری

🇬🇧

  • Database → MongoDB — no SQL, so schema changes never need migrations; updates stay fast and painless.
  • Frontend → React — light and fast UI.
  • Backend → Next.js + Node.js architecture — fast and reliable, one codebase for app + API.

🇮🇷

  • دیتابیس → MongoDB — بدون SQL؛ تغییرات شِما نیازی به migration ندارند و آپدیت‌ها سریع و بی‌دردسر می‌مانند.
  • فرانت‌اند → React — رابط کاربری سبک و سریع.
  • بک‌اند → Next.js + Node.js — سریع و قابل‌اعتماد؛ یک کدبیس برای اپ و API.

🎯 Engineering Goals | اهداف مهندسی

🇬🇧

  • Update-resilient: any update to the database or the code must never break the project — this is why SQL is avoided entirely.
  • SEO-first: every public page must be fully SEO-optimized — practical, working on-page SEO on all public routes (very important).

🇮🇷

  • مقاوم در برابر آپدیت: هیچ آپدیتی روی دیتابیس یا کد نباید پروژه را بشکند — به همین دلیل اصلاً از SQL استفاده نمی‌شود.
  • سئو محور: تمام صفحات عمومی باید سئوی کامل، کاربردی و واقعی داشته باشند (خیلی مهم).

📁 2 · Folder Structure & Code Style | ساختار پوشه‌ها و سبک کد

🗂 Project Structure | ساختار پروژه

🇬🇧 The whole project lives in src/ and must follow this exact structure:

src/
├── app/            → Frontend pages & routing
│   └── api/        → Backend & API routes
├── public/
│   ├── img/        → Site images
│   └── font/       → Site fonts
├── controllers/    → HTTP responses
├── services/       → All business logic
├── components/     → UI & styles (auth, theme, layout, ui)
└── utils/          → Libraries, realtime, helpers
.env                → Secrets: token keys, DB URI (never commit!)

🇮🇷 کل پروژه در src/ است و باید دقیقاً از این ساختار پیروی کند:

  • app → صفحه‌بندی و routing فرانت — api داخل آن: مسئول بک‌اند و APIها
  • public → عکس‌ها در img و فونت‌ها در font
  • controllers → در این قسمت responseها داده می‌شوند
  • services → کل منطق هر بخش اینجا نوشته می‌شود
  • components → UI و استایل هر بخش (زیرمجموعه‌های auth، theme، layout، ui)
  • utils → کتابخانه‌ها، ارتباط‌های real-time و کارهای جانبی و کمکی
  • .env → کلیدهای امنیتی توکن‌ها، آدرس اتصال به دیتابیس و سایر اسرار

✨ Code Style | سبک کدنویسی

🇬🇧

  • Clean code: anyone must be able to read and understand the code, so future updates stay painless.
  • Componentize everything: convert every reusable piece into a component under components/ (auth, theme, layout, ui) so the project stays scalable.

🇮🇷

  • کد تمیز: هر آدمی باید بفهمد کد چیست تا بعد از آپدیت‌ها اذیت نشوی و پروژه قابل‌توسعه بماند.
  • کامپوننت‌محور: هر بخش قابل‌استفاده را تا جای ممکن به کامپوننت تبدیل کن — این پوشه خیلی مهم است.

🚪 3 · Login Security | امنیت ورود

🚪 Login Requirements | الزامات امنیتی ورود

🇬🇧 1. Password hashing — store passwords only with Bcrypt or Argon2; plain text is forbidden. 🇮🇷 ۱. هش کردن پسورد — ذخیره‌ی رمز عبور در دیتابیس فقط با Bcrypt یا Argon2 مجاز است؛ ذخیره‌ی متن خام ممنوع.

🇬🇧 2. Rate limit — max 5 login requests per 15 minutes for each IP; violators get a temporary IP block. 🇮🇷 ۲. محدودیت تلاش (Rate Limit) — حداکثر ۵ درخواست لاگین در ۱۵ دقیقه برای هر آی‌پی؛ در صورت تخلف، بلاک موقت آی‌پی.

🇬🇧 3. Unified error message — never reveal whether the username or the password was wrong; only one generic message. 🇮🇷 ۳. پیام خطای یکپارچه — سیستم نباید بگوید یوزرنیم اشتباه است یا پسورد؛ فقط یک پیام کلی: «نام کاربری یا رمز عبور اشتباه است».

🇬🇧 4. Secure token storage — the login JWT must only live in HttpOnly + Secure cookies so XSS cannot steal it. 🇮🇷 ۴. توکن امن — توکن ورود (JWT) فقط در کوکی‌های HttpOnly و Secure قرار گیرد تا با XSS قابل‌سرقت نباشد.

🇬🇧 5. Strict input validation — every field (e.g. local full name, English username, phone number in your locale’s format such as an 11-digit Iranian mobile) must be regex-validated server-side so malicious payloads (SQLi / XSS) never reach the database. 🇮🇷 ۵. اعتبارسنجی سختگیرانه‌ی اینپوت‌ها — تمامی فیلدها (مثلاً نام کامل محلی، یوزرنیم انگلیسی، شماره تلفن با الگوی منطقه‌ی شما مثل موبایل ۱۱ رقمی ایران) باید در سمت سرور با Regex فیلتر شوند تا کدهای مخرب (SQLi/XSS) نتوانند وارد دیتابیس شوند.

🔑 4 · JWT Token System | سیستم توکن

🔑 Two Tokens, Two Secrets | دو توکن، دو کلید

🇬🇧 After login, the backend (in src/app/api/) must issue:

  • Access token — 2 minutes and Refresh token — 15 days, each signed with its own 128-character security key generated with crypto and stored in .env.
  • The samples below are Express.js — convert them for the Next.js App Router API.

🇮🇷 بعد از لاگین، بک‌اند (در src/app/api/) باید:

  • توکن دسترسی — ۲ دقیقه و توکن تازه‌سازی — ۱۵ روز را صادر کند؛ هرکدام با کلید امنیتی جداگانه‌ی ۱۲۸ کاراکتری ساخته‌شده با crypto و ذخیره‌شده در .env.
  • کدهای نمونه زیر Express.js هستند — آن‌ها را برای API بک‌اند Next.js تبدیل کن.

🟠 Access Token — Generate & Verify | ساخت و رمزگشایی

🇬🇧 Short-lived (2 min) token carrying id, role, firstName and a unique jti. 🇮🇷 توکن کوتاه‌عمر (۲ دقیقه) با id، role، firstName و شناسه‌ی یکتای jti.

Generate | ساخت:

import "dotenv/config";
import jwt from "jsonwebtoken";
import crypto from "crypto";

export default function GenerateAccessToken(user) {
  try {
    return jwt.sign(
      { id: user._id, role: user.role, firstName: user.firstName, jti: crypto.randomUUID() },
      process.env.Access_Token_Security_Code,
      { expiresIn: "2m" }
    );
  } catch (error) {
    throw error;
  }
}

Verify | رمزگشایی:

import "dotenv/config";
import jwt from "jsonwebtoken";

export default function verifyAccessToken(token) {
  try {
    return jwt.verify(token, process.env.Access_Token_Security_Code);
  } catch (error) {
    return null;
  }
}

🍪 Access Token Cookie | کوکی توکن دسترسی

🇬🇧 HttpOnly, Secure in production, 2-minute lifespan. 🇮🇷 کوکی HttpOnly و Secure در پروداکشن با عمر ۲ دقیقه.

res.cookie("accessToken", accessToken, {
  httpOnly: true,
  secure: process.env.NODE_ENV === "production",
  sameSite: "strict",
  maxAge: 2 * 60 * 1000,
});

⚠️ 🇬🇧 Set SameSite to strict/lax here as well — required by the CSRF policy in the OWASP group (the early draft used an empty value). ⚠️ 🇮🇷 SameSite را اینجا هم strict/lax بگذار — طبق سیاست CSRF در گروه OWASP (پیش‌نویس اولیه مقدار خالی داشت).

🔵 Refresh Token — Generate & Verify | ساخت و رمزگشایی

🇬🇧 Long-lived (15 days) token with its own 128-char secret key; carries id, firstName, jti. 🇮🇷 توکن بلندعمر (۱۵ روز) با کلید امنیتی ۱۲۸ کاراکتری جدا؛ شامل id، firstName و jti.

Generate | ساخت:

import "dotenv/config";
import jwt from "jsonwebtoken";
import crypto from "crypto";

export default function GenerateRefreshToken(user) {
  try {
    return jwt.sign(
      { id: user._id, firstName: user.firstName, jti: crypto.randomUUID() },
      process.env.Refresh_Token_Security_Code,
      { expiresIn: "15d" }
    );
  } catch (error) {
    throw error;
  }
}

Verify | رمزگشایی:

import "dotenv/config";
import jwt from "jsonwebtoken";

export default function verifyRefreshToken(token) {
  try {
    return jwt.verify(token, process.env.Refresh_Token_Security_Code);
  } catch (error) {
    return null;
  }
}

🍪➡️ 🚪 Refresh Cookie & Logout | کوکی تازه‌سازی و خروج

🇬🇧 The refresh cookie lives 15 days; logout clears both cookies with identical flags. 🇮🇷 کوکی تازه‌سازی ۱۵ روز عمر دارد؛ خروج هر دو کوکی را با همان فلگ‌ها پاک می‌کند.

Refresh cookie | کوکی تازه‌سازی:

res.cookie("refreshToken", refreshToken, {
  httpOnly: true,
  secure: process.env.NODE_ENV === "production",
  sameSite: "strict",
  maxAge: 15 * 24 * 60 * 60 * 1000,
});

Logout — clear both cookies | خروج — پاک‌کردن هر دو کوکی:

export default function ClearTokenCookies(res) {
  res.clearCookie("accessToken", {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    sameSite: "strict",
  });
  res.clearCookie("refreshToken", {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    sameSite: "strict",
  });
}

🛡 5 · Post-Login Security | امنیت پس از ورود

⏱ Session Management | مدیریت نشست

🇬🇧

  • Idle timeout: 15–30 min of inactivity → the session expires and the user must log in again.
  • Absolute timeout: even active users are logged out after ~8 hours so stolen long-lived tokens become useless.
  • Single active session: a user must not be logged in from two devices/browsers at once; a new login instantly invalidates the previous session.

🇮🇷

  • انقضای بی‌فعالیتی: ۱۵ تا ۳۰ دقیقه بی‌فعالیتی → سشن خودکار منقضی شود و کاربر دوباره لاگین کند.
  • انقضای مطلق: حتی اگر کاربر مدام فعال باشد، بعد از مثلاً ۸ ساعت سشن قطع شود تا توکن‌های سرقت‌شده‌ی طولانی‌مدت کار نکنند.
  • کنترل ورود همزمان: یک کاربر نباید همزمان از دو دستگاه یا دو مرورگر وارد شود؛ ورود جدید، سشن دستگاه قبلی را فوراً باطل کند.

🧱 Data Isolation & IDOR | جداسازی داده و جلوگیری از IDOR

🇬🇧 RBAC isolation

  • A user must never see another user’s files, tasks, messages or customer data.
  • Every database query must filter by the logged-in user (user_id = current user).
  • Only admins may see global reports and every user’s data.

🇬🇧 IDOR prevention

  • Changing an id in the API URL (e.g. /api/files/101 → /api/files/102) must never return someone else’s data.
  • The server must verify ownership of every requested id against the logged-in user; prefer UUIDs over sequential ids (helpful, not sufficient alone).

🇮🇷 جداسازی نقش‌محور (RBAC)

  • کاربر تحت هیچ شرایطی نباید فایل‌ها، تسک‌ها، پیام‌ها و داده‌ی مشتریانِ کاربر دیگر را ببیند.
  • همه‌ی کوئری‌های دیتابیس باید فیلتر user_id = کاربر لاگین‌شده داشته باشند.
  • فقط مدیران (admin) باید بتوانند گزارش‌های کلان و داده‌های همه‌ی کاربران را ببینند.

🇮🇷 جلوگیری از IDOR

  • هکر نباید با تغییر آیدی در آدرس API (مثلاً /api/files/101 به /api/files/102) به داده‌ی شخص دیگری دسترسی پیدا کند.
  • سرور در هر درخواست باید مالکیت آیدی را نسبت به یوزر لاگین‌شده چک کند؛ استفاده از UUID به‌جای آیدی ترتیبی (کمکی، نه کامل).

😶 Data Masking | ماسک‌کردن اطلاعات حساس

🇬🇧 Sensitive customer data — phone numbers above all — is the crown jewels of any product. In list views it must appear masked (e.g. 0912****567); the full value is revealed only through a “View” button — and every reveal is logged. This stops a rogue user or employee from bulk-exporting the data.

🇮🇷 داده‌های حساس مشتریان — بالاخص شماره تماس — ارزشمندترین دارایی هر محصول است. در لیست‌ها باید ماسک‌شده نمایش داده شود (مثلاً 0912****567)؛ نمایش کامل فقط با کلیک روی دکمه‌ی «مشاهده» انجام شود که در لاگ ثبت می‌گردد. این کار از خروجی‌گرفتن دسته‌جمعی دیتا توسط کاربر یا کارمند سوءاستفاده‌گر جلوگیری می‌کند.

📎 File Upload Security | امنیت آپلود فایل

🇬🇧 For user uploads (images, documents, PDFs — adapt the whitelist to your product):

  • Only whitelisted formats are accepted (e.g. jpg, png, pdf) — check the extension and the MIME type.
  • Filenames are randomized on the server so users cannot guess storage paths.
  • Uploaded files get no execute permission → hacker web shells cannot run.
  • Store uploads in cloud storage, never inside the code or the database — apply this across the whole project wherever uploads exist.

🇮🇷 برای فایل‌های آپلودی کاربران (عکس، مدرک، PDF — لیست مجاز را مطابق محصول خود تنظیم کنید):

  • فقط فرمت‌های مجاز از Whitelist (مثل jpg، png، pdf) پذیرفته شود — با بررسی پسوند و MIME Type.
  • نام فایل‌ها در سرور به‌صورت رندوم تغییر کند تا کاربر نتواند مسیر سرور را حدس بزند.
  • فایل‌های آپلودی نباید دسترسی اجرایی (Execute) داشته باشند تا از آپلود و اجرای شل‌های هکری (Web Shell) جلوگیری شود.
  • ذخیره‌سازی در فضای ابری، نه داخل کد یا دیتابیس — در تمام بخش‌هایی که آپلود دارند اعمال شود.

🤖 Chat & AI Security | امنیت چت و هوش مصنوعی

🇬🇧

  • Internal chat: messages must be sanitized before storage so users cannot inject malicious scripts (XSS) into messages.
  • AI inputs: every request needs a rate limit + character-length limit, so a single user cannot inflate your AI API costs with heavy requests (prompt-injection & abuse protection).

🇮🇷

  • چت داخلی: پیام‌ها باید قبل از ذخیره در دیتابیس پاکسازی (Sanitize) شوند تا کاربران نتوانند کدهای مخرب (XSS) در پیام‌ها قرار دهند.
  • ورودی هوش مصنوعی: درخواست‌ها باید محدودیت تعداد (Rate Limit) و طول کاراکتر داشته باشند تا یک کاربر با ارسال درخواست‌های سنگین، هزینه‌ی API هوش مصنوعی را بالا نبرد (محافظت از Prompt Injection).

📜 Audit Trail | لاگ‌گیری اقدامات حساس

🇬🇧 Every sensitive action — viewing sensitive data, editing or deleting records, downloading files — must be logged in a log table with IP + timestamp + username + action type, so if information ever leaks, the administrator can trace exactly who leaked what, and when.

🇮🇷 هر اقدام حساس — مشاهده‌ی داده‌ی حساس، تغییر یا حذف رکورد، دانلود فایل — باید در جدول لاگ با ثبت آی‌پی + زمان + یوزرنیم + نوع عملیات ذخیره شود تا در صورت لو رفتن اطلاعات، مدیر سیستم دقیقاً بفهمد چه کسی، چه چیزی را، کِی لو داده است.

🐞 6 · OWASP Top 10 Checklist | چک‌لیست ده تهدید امنیتی وب

🐞 Threats 1–5 | تهدیدهای ۱ تا ۵

1 — SQL Injection | تزریق SQL 🇬🇧 Attackers must never be able to inject malicious SQL through user inputs — e.g. bypassing login with ’ OR 1=1 --. Sanitize every input. 🇮🇷 مهاجم نبتواند از طریق ورودی‌های کاربر دستورات SQL مخرب به دیتابیس تزریق کند و نتواند با ’ OR 1=1 -- احراز هویت را دور بزند.

2 — XSS | اسکریپت‌نویسی بین‌سایتی 🇬🇧 All three types — Reflected, Stored, DOM-based — must be blocked; otherwise attackers run malicious JavaScript in the victim’s browser to steal cookies/sessions or tamper with user actions. 🇮🇷 هر سه نوع — Reflected، Stored و DOM-based — باید مسدود باشند؛ وگرنه مهاجم جاوااسکریپت مخرب در مرورگر قربانی اجرا می‌کند، کوکی‌ها را می‌دزدد، سشن را می‌قاپد یا عملیات کاربران را تغییر می‌دهد.

3 — CSRF | جعل درخواست بین‌سایتی 🇬🇧 Browsers auto-send cookies with every request; attackers trick users into unwanted actions (money transfer, password change). Fix: CSRF Token in forms + SameSite=Strict/Lax cookies + re-confirmation for sensitive operations. 🇮🇷 مرورگر قربانی خودکار کوکی‌ها را همراه درخواست می‌فرستد؛ مهاجم با فریب کاربر باعث ارسال درخواست ناخواسته می‌شود. راه‌حل: توکن CSRF در فرم‌ها + فلگ SameSite=Strict/Lax روی کوکی‌ها + درخواست مجوز مجدد برای عملیات‌های حساس.

4 — IDOR | ارجاع مستقیم ناامن 🇬🇧 See the Data Isolation & IDOR card in group 5 — server-side authorization per request, Object-Level Authorization, UUIDs. 🇮🇷 کارت جداسازی داده و IDOR در گروه ۵ را ببینید — بررسی دسترسی در سمت سرور برای هر درخواست، Object-Level Authorization و UUID.

5 — Authentication Failures | شکست در احراز هویت و مدیریت سشن 🇬🇧 Weak/default passwords, session hijacking (XSS/sniffing), session fixation, no session expiry, no rate limit on login (brute force). Fix: Secure + HttpOnly + SameSite cookies, session expiry + id regeneration after login, account lockout after failed attempts. 🇮🇷 رمزهای ضعیف یا پیش‌فرض، Session Hijacking، Session Fixation، عدم انقضای نشست‌ها، نبود Rate Limit در لاگین (امکان Brute Force). راه‌حل: کوکی‌های Secure/HttpOnly/SameSite، انقضای سشن و بازتولید شناسه بعد از لاگین و قفل حساب پس از تلاش‌های ناموفق.

🐞 Threats 6–10 | تهدیدهای ۶ تا ۱۰

8 — Security Misconfiguration | پیکربندی ناامن 🇬🇧 Debug mode in production, directory listing enabled, default pages & server version banners (e.g. Server: Apache 2.4.49), CORS set to *, unprotected admin panels. Fix: regular package updates, review the details, remove unused dependencies. 🇮🇷 استفاده از کتابخانه‌ها و فریم‌ورک‌های قدیمی با آسیب‌پذیری شناخته‌شده. راه‌حل: به‌روزرسانی منظم پکیج‌ها، بررسی جزئیات و حذف وابستگی‌های استفاده‌نشده.

Next.js Project Structure — Folder & Code Style Prompt

You are scaffolding a Next.js + MongoDB application. Follow this structure and code style exactly so the project stays clean, readable and scalable as it grows.

1 · Folder Tree

The whole project lives in src/ with this exact layout:

  • src/app/ → frontend pages & routing
    • src/app/api/ → backend & API routes (one folder per resource: auth, users, files, …)
  • src/public/img/ → site images
  • src/public/font/ → site fonts
  • src/controllers/ → HTTP layer: parse requests, call services, return responses — no business logic here
  • src/services/ → ALL business logic — controllers and components never talk to the database directly
  • src/components/ → every reusable UI piece, grouped by domain: auth/, theme/, layout/, ui/
  • src/utils/ → libraries, realtime connections, helpers
  • .env → secrets: token keys, DB URI (never commit!)

  1. Request flow is always: route → controller → service → database. Never skip a layer.
  2. Controllers return one consistent response shape: { success, message, data }.

  • Clean code: anyone on the team must be able to read and understand any file without a briefing.
  • Componentize every reusable piece under components/ — duplicated UI is a bug.
  • Name files by domain, not by type: services/auth-service.js, components/auth/login-form.jsx.
  • Keep functions small and single-purpose; extract anything reused into utils/.
  • Comment only the "why", never the "what".

4 · Scalability Checks

  • Adding a new feature = adding folders under app/, controllers/, services/, components/ — no structural rewrites.
  • Any update to the schema or code must never break the project (update-resilient goal — MongoDB, no migrations).
  • Every public page is fully SEO-optimized (metadata, semantic HTML, performance).

Production Deploy Runbook — اجرا، استقرار، راستی‌آزمایی

جمع‌بندی تجربه‌ی عملی استقرار Next.js روی ویندوز. قواعد پورت و سیکل دیپلوی باید با سیاست مدیر پروژه هماهنگ باشد و تغییراتش مستند.

۱) پورت dev/پروداکشن — مالکیت و تصاحب

  • پورت اصلی = بیلد پروداکشن (next start)، هرگز next dev.
  • اگر پورت اشغال بود: پیدا کن، بکش، خودت بالا بیاور:
    netstat -ano | grep ":3000" | grep LISTENING        # PIDها
for pid in $(netstat -ano | grep ":3000" | grep LISTENING | awk '{print $NF}' | sort -u); do taskkill //PID $pid //F; done
  • هرگز دو سرور روی یک پورت نباشد — دو پروسه‌ی هم‌زمان = BUILD_ID از .next خراب می‌شود/UI ناقص لود می‌شود. علامت بیماری: چند PID روی پورت + ls .next/BUILD_ID خالی → کلین‌بیلد از نو.
  • پروسه‌های بک‌گراند npm/next start گاهی «exit 1» گزارش می‌شوند درحالی‌که سالم‌اند — همیشه با curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/ تصمیم بگیر، نه با status تسک.

۲) سیکل دیپلوی (توقف → بیلد → استارت)

بیلد روی سرورِ در حال اجرا ممنوع — ویندوز روی فایل‌های .next قفل می‌گذارد و بیلد/استارت دوم با «Could not find production build» می‌میرد. ترتیب همیشه:

# ۱) توقف
for pid in $(netstat -ano | grep ":3000" | grep LISTENING | awk '{print $NF}' | sort -u); do taskkill //PID $pid //F; done
# ۲) بیلد
npm run build
# ۳) استارت (بک‌گراند) — فقط یک پروسه روی پورت
npx next start
# ۴) تأیید
curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/     # 200
  • اگر خروجی بیلد دوپهلو بود («Compiled successfully» و «Failed» با هم) — اجرای مجدد تمیز بگیر؛ اغلب خروجی نیمه‌کاره‌ی یک اجرای قطع‌شده است.
  • خروجی «Failed to compile» واقعی = دوباره npm run build 2>&1 | tail -25 بگیر و خطا را بخوان.

۳) راستی‌آزمایی — قبل از هر کامیت

  1. npx tsc --noEmit → صفر خطا.
  2. npx eslint <فایل‌های دست‌خورده> → صفر خطا (هشدارهای قدیمی‌شناخته اشکال ندارد).
  3. سئو: اسکریپت چک سئوی پروژه را روی سرور لوکال اجرا کن (robots، متاها، X-Robots-Tag، 404 واقعی).
  4. بصری: مرورگر in-app — دسکتاپ ۱۴۴۰×۹۰۰ + موبایل ۳۹۰×۸۴۴، اسکرین‌شات؛ برای اندازه‌گیری دقیق از tab.playwright.evaluate استفاده کن (عدد بده، حدس نزن).
  5. تست تعاملی (کلیک/فرم): اگر locator با نام فارسی timeout خورد، دوباره همان را retry نکن — tab.playwright.evaluate با document.querySelector(...).click() قطعی‌تر است، یا کلیک با مختصات از اسکرین‌شات تازه.

سرور موقت موازی (بدون دست زدن به پورت اصلی)

NEXT_DIST_DIR=.next-verify npx next build     # خروجی جدا — در .gitignore است
NEXT_DIST_DIR=.next-verify npx next start -p 3100
# بعد از کار: هر PID لیسنر 3100 را taskkill کن

پورت اصلی برای تغییرِ env/CSS فقط با بیلد+ری‌استارت خودش به‌روز می‌شود.

۴) دیتابیس — بکاپ و مهاجرت

  • دیتابیس پروداکشن معمولاً لوکال است؛ رشته‌ی اتصال فقط از .env خوانده شود.
  • بکاپ: اگر mongodump نصب نیست، اکسپورت JSON همه کالکشن‌ها به backups/db-<timestamp>/ (اسکریپت کوتاه با connectDB + mongoose.connection.db.collections()). پوشه backups/ در .gitignore — دیتای کاربران دارد، هرگز کامیت نشود.
  • اسکریپت‌های مستقل tsx: .env را خودشان باید لود کنند (tsx خودش نمی‌خواند) و در پایان mongoose.connection.close() یا process.exit() — وگرنه پروسه باز می‌ماند و «هنگ» به نظر می‌رسد.
  • مهاجرت داده: همیشه اول dry-run، بعد --write؛ الگوی idempotent (upsert با کلید یکتا).

۵) سئو — قواعد حیاتی

  • NEXT_PUBLIC_SITE_URL هرگز localhost نماند — اگر robots.ts حالت staging داشته باشد، با URL لوکال کل سایت Disallow: / می‌شود + canonical/sitemap لوکالی می‌شوند. (NEXT_PUBLIC_* در build اینلاین می‌شود → تغییرش = بیلد مجدد.)
  • ریدایرکت‌های غیرASCII در next.config باید encodeURI(from) باشند — Next فاز redirects را روی مسیر percent-encoded مقایسه می‌کند.
  • فونت فارسی با display:"swap" + preload — سقف ۴ وزن.
  • گیت سئو: چک‌لیست robots، متای صفحات، X-Robots-Tag روی /api و 404 واقعی.

۶) دام‌های شناخته‌شده (هرکدام یک بار گاز گرفته‌اند)

  • CSS cascade: override فقط-موبایل را همیشه بعد از قانون پایه بنویس؛ قانون هم‌وزنِ قبلیِ فایل می‌بَرد. قانون base معمولاً پایین‌تر از جایی است که فکر می‌کنی.
  • .gitignore: خط با \n لفظی = قانون بی‌اثر. بعد از هر افزودن، git status را چک کن.
  • sed با متن فارسی/یونیکد روی این ماشین می‌شکند (ugrep alias + یونیکد) — از ابزار Edit استفاده کن؛ برای grep الگو با grep -oe 'pattern'.
  • تصاویر: next/image پیش‌فرض lazy — فقط LCP واقعی priority بگیرد.

۷) گیت — قرارداد کامیت/پوش

  • کامیت‌های conventional: feat|fix|style|refactor|docs|chore(scope): خلاصه انگلیسی.
  • قبل از کامیت npx tsc --noEmit.
  • سیاست پوش با دستور مدیر مستند شود (پوش آزاد، فقط با دستور، یا از دیپلوی خودکار).
  • وقتی ایجنت دیگر هم‌زمان در کلون کار می‌کند: فایل‌های خودت را صریح add کن (نه add -A) مگر مدیر گفته باشد «همه‌چیز را کامیت کن» — آن‌وقت یک کامیت جدا با توضیح «agent work» بده.
  • فایل‌های مشترک حساس: .env هرگز؛ فایل‌های استایل/برد نقطه تماس دو ایجنت‌اند — قبل از کامیت git diff آن‌ها را نگاه کن که کار طرف دیگر را قاطی نکنی.

Next.js SEO — Complete Google Optimization Guide

Implement production-grade Google SEO in Next.js (Node.js) projects. This skill encodes Google Search Central documentation plus current Next.js (v15/v16, App Router first) conventions into a review-and-implementation workflow.

How Google Search Works (30-second mental model)

Google processes every URL in four stages. Every SEO task maps to one of them:

  1. Crawl — Googlebot discovers URLs via links, sitemaps, and previously known URLs. robots.txt, noindex, and server errors control this.
  2. Render — Googlebot executes JavaScript with an evergreen Chromium (Web Rendering Service). SSR/SSG pages render instantly; JS-only content enters a slower second wave. Server-rendered HTML is always safer.
  3. Index — Google parses the rendered HTML, resolves canonicals, groups duplicate URLs, and stores content. <link rel="canonical">, noindex, and hreflang act here.
  4. Rank — Helpful-content signals, relevance, links, page experience (Core Web Vitals), and spam policies determine position.

Rule of thumb: ship real content in the initial HTML response, describe every page with unique metadata, remove crawl/index blockers, and keep the page fast and stable.

Core Workflow

When building or auditing a Next.js project, work through these steps in order:

Step 1 — Establish the base (every project)

// app/layout.tsx — root layout
import type { Metadata, Viewport } from 'next'

const SITE_URL = 'https://example.com' // single source of truth

export const metadata: Metadata = {
  metadataBase: new URL(SITE_URL), // resolves all relative URLs — REQUIRED for OG images
  title: {
    default: 'Site Name — Primary value proposition',
    template: '%s — Site Name', // child pages only need `title`
  },
  description: 'Default site-wide description, 150–160 chars, unique per page when possible.',
  alternates: { canonical: '/' },
  openGraph: {
    type: 'website',
    siteName: 'Site Name',
    url: SITE_URL,
  },
}

export const viewport: Viewport = {
  width: 'device-width',
  initialScale: 1,
  themeColor: '#000000',
}

// app/page.tsx — home page
import type { Metadata } from 'next'
export const metadata: Metadata = {
  title: 'Home', // renders as "Home — Site Name" via template
  alternates: { canonical: '/' },
}

Key API facts:

  • metadata = static export; generateMetadata() = dynamic, receives awaited params/searchParams (Next 15+: they are Promises).
  • Metadata only works in Server Components. Next always adds charset and viewport meta tags automatically.
  • Merge rules: fields are shallow-merged from root layout down. A child's title overrides the parent's whole title object; openGraph.title falls back to title when omitted.
  • themeColor/viewport inside metadata are deprecated since Next 14 — use the viewport/generateViewport exports.
  • Next 15.2+ streams metadata for human users but emits blocking <head> metadata for bots (Googlebot, Bingbot, Twitterbot…) — configurable via htmlLimitedBots. Bots still see correct tags; do not panic when you see tags in <body> for a non-bot UA.
  • Next 16: params/searchParams must be awaited; Turbopack is default; middleware.ts → proxy.ts; Cache Components model with "use cache".

Step 2 — Control crawling and indexing

  • app/robots.ts → generates /robots.txt (allow public paths, block /api, admin, search results pages).
  • app/sitemap.ts → generates /sitemap.xml from your routes/CMS (split with generateSitemaps beyond 50,000 URLs).
  • Canonical URLs: set alternates.canonical on every indexable page, especially filtered/sorted/paginated variants.
  • Block indexing with robots: { index: false } (meta robots) — never with robots.txt (Google explicitly does not support noindex in robots.txt).
  • Non-HTML resources: use the X-Robots-Tag HTTP header via next.config.ts headers().
  • Redirects: permanent: true (308/301) for moved content, temporary otherwise; declare in next.config.ts.

Step 3 — Add structured data (JSON-LD)

Emit <script type="application/ld+json"> from Server Components. Minimum set per site type:

Site type Schemas
Any site Organization, WebSite (+ SearchAction), BreadcrumbList
Blog / news Article / BlogPosting / NewsArticle
E-commerce Product + Offer + AggregateRating, Review
Local business LocalBusiness (+ subtypes), Event
Docs / how-to HowTo, TechArticle, FAQPage (visible on page) 
// app/blog/[slug]/page.tsx
export default async function Page({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params
  const post = await getPost(slug)
  const jsonLd = {
    '@context': 'https://schema.org',
    '@type': 'BlogPosting',
    headline: post.title,
    datePublished: post.date,
    image: post.cover,
    author: { '@type': 'Person', name: post.author.name },
  }
  return (
    <>
      <script
        type="application/ld+json"
        dangerouslySetInnerHTML={{ __html: JSON.stringify(jsonLd) }}
      />
      <article>{/* content */}</article>
    </>
  )
}

Step 4 — Social sharing (Open Graph + Twitter)

  • metadata.openGraph + metadata.twitter objects, or file conventions: opengraph-image.png, twitter-image.png, icon.png, apple-icon.png per route segment.
  • Dynamic OG images: opengraph-image.tsx with ImageResponse from next/og (1200×630, flexbox-only CSS subset).
  • Always provide absolute-resolvable images (needs metadataBase) with width/height/alt.

Step 5 — Core Web Vitals (page experience)

Thresholds (75th percentile of real-user visits, from CrUX): LCP ≤ 2.5 s · INP ≤ 200 ms · CLS ≤ 0.1 (INP replaced FID in March 2024).

Next.js levers, in impact order:

  1. next/image everywhere; priority on the LCP image; correct sizes.
  2. next/font/google / next/font/local (self-hosted, subset, no render-blocking Google CSS, adjustFontFallback kills font CLS).
  3. Server Components by default; "use client" only at leaves.
  4. next/script with proper strategy for third-party tags; afterInteractive default, lazyOnload for widgets.
  5. Streaming + Suspense for fast FCP; static/ISR rendering for TTFB.

Step 6 — Rendering strategy per page type (SEO-critical decision)

Page type Strategy Why
Marketing / home Static (default) Instant TTFB, zero config
Blog / docs Static or ISR (revalidate) Freshness without SSR cost
E-commerce PDP ISR or dynamic w/ cache Price/stock freshness vs speed
Search results, cart Dynamic (SSR) Per-request personalization
Dashboard (auth) Client + noindex Not for Google anyway

Next 16 Cache Components: enable cacheComponents: true, wrap dynamic data with "use cache" + cacheLife(); PPR shells stream instantly while dynamic holes fill in — bots get a complete, cached HTML shell.

Step 7 — Internationalization (if multi-language)

  • App Router pattern: app/[lang]/ dynamic segment; render localized metadata via generateMetadata.
  • hreflang: alternates.languages with x-default; every URL pair must be reciprocal.
  • Locales in URLs (/en/…, /de/…) is Google's recommended structure.

Step 8 — Pages Router projects

If the project uses pages/ (not app/): <Head> component, getStaticProps/getServerSideProps, manual canonical/OG tags.

Step 9 — Validate and monitor

  1. next build — watch for metadata warnings (metadataBase missing, prerender errors).
  2. Google Rich Results Test + Schema.org validator for JSON-LD.
  3. PageSpeed Insights / Lighthouse for CWV; Search Console for indexing, sitemaps, rich results.
  4. Re-crawl after changes: URL Inspection → "Request indexing".

Non-Negotiable Rules

These prevent the most common, highest-impact failures seen in real Next.js projects:

  1. One canonical URL per page. Missing or self-conflicting canonicals dilute ranking across ?filter=, trailing-slash, and http/https variants.
  2. Never rely on robots.txt to de-index. noindex belongs in meta robots or X-Robots-Tag. Blocking via robots.txt hides the page from the crawler but leaves the URL indexed "without content".
  3. Set metadataBase in the root layout. Without it, OG image URLs warn or resolve wrong; social cards break silently.
  4. Every indexable page needs a unique title + description. Templated or duplicated descriptions get rewritten by Google; titles get truncated past ~600 px.
  5. Server-render indexable content. Content only mounted after user interaction or fetch-on-client is invisible until render — often never indexed.
  6. priority the LCP image, sizes every image. Wrong sizes wastes bandwidth; missing priority on the hero image tanks LCP.
  7. JSON-LD must mirror visible content. Structured data describing invisible/fabricated content violates Google's spam policies.
  8. Await params/searchParams. Next 15+ they are Promises; sync access throws at build.
  9. Keep viewport out of metadata. Use the viewport/generateViewport export (deprecated-in-14 fields still render but warn).
  10. Use 308/301 (permanent: true) for content moves, and only one redirect hop. Chains leak PageRank and delay crawls.

Launch-Ready SEO Checklist (condensed)

  • metadataBase + title template + default OG in root layout
  • Unique title/description/canonical per indexable route
  • robots.ts allows pages, blocks /api, /admin, internal search
  • sitemap.ts lists all canonical, indexable URLs with lastModified
  • JSON-LD for site type + BreadcrumbList on nested pages
  • opengraph-image per key route (1200×630) + favicon/icon set
  • next/image with sizes; priority on hero; next/font for all text
  • noindex on utility pages (404 intentionally excluded, thank-you, admin)
  • 301 redirects map for any moved/renamed routes
  • hreflang alternates.languages + x-default if multi-language
  • Verified in Search Console; sitemap submitted; zero "Page indexing" errors
  • PSI field data: LCP < 2.5 s, INP < 200 ms, CLS < 0.1
