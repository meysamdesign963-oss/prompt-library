🔐 Security Blueprint — Universal Web App Spec

نقشه‌ی جامع امنیت و مهندسی — پرامپت عمومی برای هر اپلیکیشن وب

🇬🇧 A project-agnostic security & engineering blueprint for any web application built with Next.js + MongoDB. Copy this canvas into your repo and hand it to a developer or an AI coding agent as a ready-made spec/prompt. Follow the numbered groups and the arrows (1 → 6). Every card explains the topic in English first, then Persian.

🇮🇷 یک بلوپرینت مستقل از نوع پروژه برای امنیت و مهندسی هر اپلیکیشن وب با Next.js + MongoDB. این کانواز را در ریپوی خود کپی کنید و به‌عنوان پرامپت/اسپک آماده به توسعه‌دهنده یا ایجنت هوش مصنوعی بدهید. گروه‌های شماره‌دار و فلش‌ها را دنبال کنید (۱ تا ۶). هر کارت اول انگلیسی و بعد فارسی توضیح داده شده است.

1️⃣ Architecture معماری → 2️⃣ Structure ساختار → 3️⃣ Login ورود → 4️⃣ Tokens توکن‌ها → 5️⃣ Post-Login پس از ورود → 6️⃣ OWASP

🏗 1 · Architecture & Tech Stack | معماری و پشته‌ی فناوری

🧱 Tech Stack | پشته‌ی فناوری

🇬🇧

  • Database → MongoDB — no SQL, so schema changes never need migrations; updates stay fast and painless.
  • Frontend → React — light and fast UI.
  • Backend → Next.js + Node.js architecture — fast and reliable, one codebase for app + API.

🇮🇷

  • دیتابیس → MongoDB — بدون SQL؛ تغییرات شِما نیازی به migration ندارند و آپدیت‌ها سریع و بی‌دردسر می‌مانند.
  • فرانت‌اند → React — رابط کاربری سبک و سریع.
  • بک‌اند → Next.js + Node.js — سریع و قابل‌اعتماد؛ یک کدبیس برای اپ و API.

🎯 Engineering Goals | اهداف مهندسی

🇬🇧

  • Update-resilient: any update to the database or the code must never break the project — this is why SQL is avoided entirely.
  • SEO-first: every public page must be fully SEO-optimized — practical, working on-page SEO on all public routes (very important).

🇮🇷

  • مقاوم در برابر آپدیت: هیچ آپدیتی روی دیتابیس یا کد نباید پروژه را بشکند — به همین دلیل اصلاً از SQL استفاده نمی‌شود.
  • سئو محور: تمام صفحات عمومی باید سئوی کامل، کاربردی و واقعی داشته باشند (خیلی مهم).

📁 2 · Folder Structure & Code Style | ساختار پوشه‌ها و سبک کد

🗂 Project Structure | ساختار پروژه

🇬🇧 The whole project lives in src/ and must follow this exact structure:

src/
├── app/            → Frontend pages & routing
│   └── api/        → Backend & API routes
├── public/
│   ├── img/        → Site images
│   └── font/       → Site fonts
├── controllers/    → HTTP responses
├── services/       → All business logic
├── components/     → UI & styles (auth, theme, layout, ui)
└── utils/          → Libraries, realtime, helpers
.env                → Secrets: token keys, DB URI (never commit!)

🇮🇷 کل پروژه در src/ است و باید دقیقاً از این ساختار پیروی کند:

  • app → صفحه‌بندی و routing فرانت — api داخل آن: مسئول بک‌اند و APIها
  • public → عکس‌ها در img و فونت‌ها در font
  • controllers → در این قسمت responseها داده می‌شوند
  • services → کل منطق هر بخش اینجا نوشته می‌شود
  • components → UI و استایل هر بخش (زیرمجموعه‌های auth، theme، layout، ui)
  • utils → کتابخانه‌ها، ارتباط‌های real-time و کارهای جانبی و کمکی
  • .env → کلیدهای امنیتی توکن‌ها، آدرس اتصال به دیتابیس و سایر اسرار

✨ Code Style | سبک کدنویسی

🇬🇧

  • Clean code: anyone must be able to read and understand the code, so future updates stay painless.
  • Componentize everything: convert every reusable piece into a component under components/ (auth, theme, layout, ui) so the project stays scalable.

🇮🇷

  • کد تمیز: هر آدمی باید بفهمد کد چیست تا بعد از آپدیت‌ها اذیت نشوی و پروژه قابل‌توسعه بماند.
  • کامپوننت‌محور: هر بخش قابل‌استفاده را تا جای ممکن به کامپوننت تبدیل کن — این پوشه خیلی مهم است.

🚪 3 · Login Security | امنیت ورود

🚪 Login Requirements | الزامات امنیتی ورود

🇬🇧 1. Password hashing — store passwords only with Bcrypt or Argon2; plain text is forbidden. 🇮🇷 ۱. هش کردن پسورد — ذخیره‌ی رمز عبور در دیتابیس فقط با Bcrypt یا Argon2 مجاز است؛ ذخیره‌ی متن خام ممنوع.

🇬🇧 2. Rate limit — max 5 login requests per 15 minutes for each IP; violators get a temporary IP block. 🇮🇷 ۲. محدودیت تلاش (Rate Limit) — حداکثر ۵ درخواست لاگین در ۱۵ دقیقه برای هر آی‌پی؛ در صورت تخلف، بلاک موقت آی‌پی.

🇬🇧 3. Unified error message — never reveal whether the username or the password was wrong; only one generic message. 🇮🇷 ۳. پیام خطای یکپارچه — سیستم نباید بگوید یوزرنیم اشتباه است یا پسورد؛ فقط یک پیام کلی: «نام کاربری یا رمز عبور اشتباه است».

🇬🇧 4. Secure token storage — the login JWT must only live in HttpOnly + Secure cookies so XSS cannot steal it. 🇮🇷 ۴. توکن امن — توکن ورود (JWT) فقط در کوکی‌های HttpOnly و Secure قرار گیرد تا با XSS قابل‌سرقت نباشد.

🇬🇧 5. Strict input validation — every field (e.g. local full name, English username, phone number in your locale’s format such as an 11-digit Iranian mobile) must be regex-validated server-side so malicious payloads (SQLi / XSS) never reach the database. 🇮🇷 ۵. اعتبارسنجی سختگیرانه‌ی اینپوت‌ها — تمامی فیلدها (مثلاً نام کامل محلی، یوزرنیم انگلیسی، شماره تلفن با الگوی منطقه‌ی شما مثل موبایل ۱۱ رقمی ایران) باید در سمت سرور با Regex فیلتر شوند تا کدهای مخرب (SQLi/XSS) نتوانند وارد دیتابیس شوند.

🔑 4 · JWT Token System | سیستم توکن

🔑 Two Tokens, Two Secrets | دو توکن، دو کلید

🇬🇧 After login, the backend (in src/app/api/) must issue:

  • Access token — 2 minutes and Refresh token — 15 days, each signed with its own 128-character security key generated with crypto and stored in .env.
  • The samples below are Express.js — convert them for the Next.js App Router API.

🇮🇷 بعد از لاگین، بک‌اند (در src/app/api/) باید:

  • توکن دسترسی — ۲ دقیقه و توکن تازه‌سازی — ۱۵ روز را صادر کند؛ هرکدام با کلید امنیتی جداگانه‌ی ۱۲۸ کاراکتری ساخته‌شده با crypto و ذخیره‌شده در .env.
  • کدهای نمونه زیر Express.js هستند — آن‌ها را برای API بک‌اند Next.js تبدیل کن.

🟠 Access Token — Generate & Verify | ساخت و رمزگشایی

🇬🇧 Short-lived (2 min) token carrying id, role, firstName and a unique jti. 🇮🇷 توکن کوتاه‌عمر (۲ دقیقه) با id، role، firstName و شناسه‌ی یکتای jti.

Generate | ساخت:

import "dotenv/config";
import jwt from "jsonwebtoken";
import crypto from "crypto";

export default function GenerateAccessToken(user) {
  try {
    return jwt.sign(
      { id: user._id, role: user.role, firstName: user.firstName, jti: crypto.randomUUID() },
      process.env.Access_Token_Security_Code,
      { expiresIn: "2m" }
    );
  } catch (error) {
    throw error;
  }
}

Verify | رمزگشایی:

import "dotenv/config";
import jwt from "jsonwebtoken";

export default function verifyAccessToken(token) {
  try {
    return jwt.verify(token, process.env.Access_Token_Security_Code);
  } catch (error) {
    return null;
  }
}

🍪 Access Token Cookie | کوکی توکن دسترسی

🇬🇧 HttpOnly, Secure in production, 2-minute lifespan. 🇮🇷 کوکی HttpOnly و Secure در پروداکشن با عمر ۲ دقیقه.

res.cookie("accessToken", accessToken, {
  httpOnly: true,
  secure: process.env.NODE_ENV === "production",
  sameSite: "strict",
  maxAge: 2 * 60 * 1000,
});

⚠️ 🇬🇧 Set SameSite to strict/lax here as well — required by the CSRF policy in the OWASP group (the early draft used an empty value). ⚠️ 🇮🇷 SameSite را اینجا هم strict/lax بگذار — طبق سیاست CSRF در گروه OWASP (پیش‌نویس اولیه مقدار خالی داشت).

🔵 Refresh Token — Generate & Verify | ساخت و رمزگشایی

🇬🇧 Long-lived (15 days) token with its own 128-char secret key; carries id, firstName, jti. 🇮🇷 توکن بلندعمر (۱۵ روز) با کلید امنیتی ۱۲۸ کاراکتری جدا؛ شامل id، firstName و jti.

Generate | ساخت:

import "dotenv/config";
import jwt from "jsonwebtoken";
import crypto from "crypto";

export default function GenerateRefreshToken(user) {
  try {
    return jwt.sign(
      { id: user._id, firstName: user.firstName, jti: crypto.randomUUID() },
      process.env.Refresh_Token_Security_Code,
      { expiresIn: "15d" }
    );
  } catch (error) {
    throw error;
  }
}

Verify | رمزگشایی:

import "dotenv/config";
import jwt from "jsonwebtoken";

export default function verifyRefreshToken(token) {
  try {
    return jwt.verify(token, process.env.Refresh_Token_Security_Code);
  } catch (error) {
    return null;
  }
}

🍪➡️ 🚪 Refresh Cookie & Logout | کوکی تازه‌سازی و خروج

🇬🇧 The refresh cookie lives 15 days; logout clears both cookies with identical flags. 🇮🇷 کوکی تازه‌سازی ۱۵ روز عمر دارد؛ خروج هر دو کوکی را با همان فلگ‌ها پاک می‌کند.

Refresh cookie | کوکی تازه‌سازی:

res.cookie("refreshToken", refreshToken, {
  httpOnly: true,
  secure: process.env.NODE_ENV === "production",
  sameSite: "strict",
  maxAge: 15 * 24 * 60 * 60 * 1000,
});

Logout — clear both cookies | خروج — پاک‌کردن هر دو کوکی:

export default function ClearTokenCookies(res) {
  res.clearCookie("accessToken", {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    sameSite: "strict",
  });
  res.clearCookie("refreshToken", {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    sameSite: "strict",
  });
}

🛡 5 · Post-Login Security | امنیت پس از ورود

⏱ Session Management | مدیریت نشست

🇬🇧

  • Idle timeout: 15–30 min of inactivity → the session expires and the user must log in again.
  • Absolute timeout: even active users are logged out after ~8 hours so stolen long-lived tokens become useless.
  • Single active session: a user must not be logged in from two devices/browsers at once; a new login instantly invalidates the previous session.

🇮🇷

  • انقضای بی‌فعالیتی: ۱۵ تا ۳۰ دقیقه بی‌فعالیتی → سشن خودکار منقضی شود و کاربر دوباره لاگین کند.
  • انقضای مطلق: حتی اگر کاربر مدام فعال باشد، بعد از مثلاً ۸ ساعت سشن قطع شود تا توکن‌های سرقت‌شده‌ی طولانی‌مدت کار نکنند.
  • کنترل ورود همزمان: یک کاربر نباید همزمان از دو دستگاه یا دو مرورگر وارد شود؛ ورود جدید، سشن دستگاه قبلی را فوراً باطل کند.

🧱 Data Isolation & IDOR | جداسازی داده و جلوگیری از IDOR

🇬🇧 RBAC isolation

  • A user must never see another user’s files, tasks, messages or customer data.
  • Every database query must filter by the logged-in user (user_id = current user).
  • Only admins may see global reports and every user’s data.

🇬🇧 IDOR prevention

  • Changing an id in the API URL (e.g. /api/files/101 → /api/files/102) must never return someone else’s data.
  • The server must verify ownership of every requested id against the logged-in user; prefer UUIDs over sequential ids (helpful, not sufficient alone).

🇮🇷 جداسازی نقش‌محور (RBAC)

  • کاربر تحت هیچ شرایطی نباید فایل‌ها، تسک‌ها، پیام‌ها و داده‌ی مشتریانِ کاربر دیگر را ببیند.
  • همه‌ی کوئری‌های دیتابیس باید فیلتر user_id = کاربر لاگین‌شده داشته باشند.
  • فقط مدیران (admin) باید بتوانند گزارش‌های کلان و داده‌های همه‌ی کاربران را ببینند.

🇮🇷 جلوگیری از IDOR

  • هکر نباید با تغییر آیدی در آدرس API (مثلاً /api/files/101 به /api/files/102) به داده‌ی شخص دیگری دسترسی پیدا کند.
  • سرور در هر درخواست باید مالکیت آیدی را نسبت به یوزر لاگین‌شده چک کند؛ استفاده از UUID به‌جای آیدی ترتیبی (کمکی، نه کامل).

😶 Data Masking | ماسک‌کردن اطلاعات حساس

🇬🇧 Sensitive customer data — phone numbers above all — is the crown jewels of any product. In list views it must appear masked (e.g. 0912****567); the full value is revealed only through a “View” button — and every reveal is logged. This stops a rogue user or employee from bulk-exporting the data.

🇮🇷 داده‌های حساس مشتریان — بالاخص شماره تماس — ارزشمندترین دارایی هر محصول است. در لیست‌ها باید ماسک‌شده نمایش داده شود (مثلاً 0912****567)؛ نمایش کامل فقط با کلیک روی دکمه‌ی «مشاهده» انجام شود که در لاگ ثبت می‌گردد. این کار از خروجی‌گرفتن دسته‌جمعی دیتا توسط کاربر یا کارمند سوءاستفاده‌گر جلوگیری می‌کند.

📎 File Upload Security | امنیت آپلود فایل

🇬🇧 For user uploads (images, documents, PDFs — adapt the whitelist to your product):

  • Only whitelisted formats are accepted (e.g. jpg, png, pdf) — check the extension and the MIME type.
  • Filenames are randomized on the server so users cannot guess storage paths.
  • Uploaded files get no execute permission → hacker web shells cannot run.
  • Store uploads in cloud storage, never inside the code or the database — apply this across the whole project wherever uploads exist.

🇮🇷 برای فایل‌های آپلودی کاربران (عکس، مدرک، PDF — لیست مجاز را مطابق محصول خود تنظیم کنید):

  • فقط فرمت‌های مجاز از Whitelist (مثل jpg، png، pdf) پذیرفته شود — با بررسی پسوند و MIME Type.
  • نام فایل‌ها در سرور به‌صورت رندوم تغییر کند تا کاربر نتواند مسیر سرور را حدس بزند.
  • فایل‌های آپلودی نباید دسترسی اجرایی (Execute) داشته باشند تا از آپلود و اجرای شل‌های هکری (Web Shell) جلوگیری شود.
  • ذخیره‌سازی در فضای ابری، نه داخل کد یا دیتابیس — در تمام بخش‌هایی که آپلود دارند اعمال شود.

🤖 Chat & AI Security | امنیت چت و هوش مصنوعی

🇬🇧

  • Internal chat: messages must be sanitized before storage so users cannot inject malicious scripts (XSS) into messages.
  • AI inputs: every request needs a rate limit + character-length limit, so a single user cannot inflate your AI API costs with heavy requests (prompt-injection & abuse protection).

🇮🇷

  • چت داخلی: پیام‌ها باید قبل از ذخیره در دیتابیس پاکسازی (Sanitize) شوند تا کاربران نتوانند کدهای مخرب (XSS) در پیام‌ها قرار دهند.
  • ورودی هوش مصنوعی: درخواست‌ها باید محدودیت تعداد (Rate Limit) و طول کاراکتر داشته باشند تا یک کاربر با ارسال درخواست‌های سنگین، هزینه‌ی API هوش مصنوعی را بالا نبرد (محافظت از Prompt Injection).

📜 Audit Trail | لاگ‌گیری اقدامات حساس

🇬🇧 Every sensitive action — viewing sensitive data, editing or deleting records, downloading files — must be logged in a log table with IP + timestamp + username + action type, so if information ever leaks, the administrator can trace exactly who leaked what, and when.

🇮🇷 هر اقدام حساس — مشاهده‌ی داده‌ی حساس، تغییر یا حذف رکورد، دانلود فایل — باید در جدول لاگ با ثبت آی‌پی + زمان + یوزرنیم + نوع عملیات ذخیره شود تا در صورت لو رفتن اطلاعات، مدیر سیستم دقیقاً بفهمد چه کسی، چه چیزی را، کِی لو داده است.

🐞 6 · OWASP Top 10 Checklist | چک‌لیست ده تهدید امنیتی وب

🐞 Threats 1–5 | تهدیدهای ۱ تا ۵

1 — SQL Injection | تزریق SQL 🇬🇧 Attackers must never be able to inject malicious SQL through user inputs — e.g. bypassing login with ’ OR 1=1 --. Sanitize every input. 🇮🇷 مهاجم نبتواند از طریق ورودی‌های کاربر دستورات SQL مخرب به دیتابیس تزریق کند و نتواند با ’ OR 1=1 -- احراز هویت را دور بزند.

2 — XSS | اسکریپت‌نویسی بین‌سایتی 🇬🇧 All three types — Reflected, Stored, DOM-based — must be blocked; otherwise attackers run malicious JavaScript in the victim’s browser to steal cookies/sessions or tamper with user actions. 🇮🇷 هر سه نوع — Reflected، Stored و DOM-based — باید مسدود باشند؛ وگرنه مهاجم جاوااسکریپت مخرب در مرورگر قربانی اجرا می‌کند، کوکی‌ها را می‌دزدد، سشن را می‌قاپد یا عملیات کاربران را تغییر می‌دهد.

3 — CSRF | جعل درخواست بین‌سایتی 🇬🇧 Browsers auto-send cookies with every request; attackers trick users into unwanted actions (money transfer, password change). Fix: CSRF Token in forms + SameSite=Strict/Lax cookies + re-confirmation for sensitive operations. 🇮🇷 مرورگر قربانی خودکار کوکی‌ها را همراه درخواست می‌فرستد؛ مهاجم با فریب کاربر باعث ارسال درخواست ناخواسته می‌شود. راه‌حل: توکن CSRF در فرم‌ها + فلگ SameSite=Strict/Lax روی کوکی‌ها + درخواست مجوز مجدد برای عملیات‌های حساس.

4 — IDOR | ارجاع مستقیم ناامن 🇬🇧 See the Data Isolation & IDOR card in group 5 — server-side authorization per request, Object-Level Authorization, UUIDs. 🇮🇷 کارت جداسازی داده و IDOR در گروه ۵ را ببینید — بررسی دسترسی در سمت سرور برای هر درخواست، Object-Level Authorization و UUID.

5 — Authentication Failures | شکست در احراز هویت و مدیریت سشن 🇬🇧 Weak/default passwords, session hijacking (XSS/sniffing), session fixation, no session expiry, no rate limit on login (brute force). Fix: Secure + HttpOnly + SameSite cookies, session expiry + id regeneration after login, account lockout after failed attempts. 🇮🇷 رمزهای ضعیف یا پیش‌فرض، Session Hijacking، Session Fixation، عدم انقضای نشست‌ها، نبود Rate Limit در لاگین (امکان Brute Force). راه‌حل: کوکی‌های Secure/HttpOnly/SameSite، انقضای سشن و بازتولید شناسه بعد از لاگین و قفل حساب پس از تلاش‌های ناموفق.

🐞 Threats 6–10 | تهدیدهای ۶ تا ۱۰

6 — Sensitive Data Exposure | افشای داده‌های حساس 🇬🇧 Moving or storing sensitive data without proper encryption. Fix: HTTPS mandatory (TLS 1.2+ & HSTS); never MD5/unsalted hashes — bcrypt/Argon2 only; encrypt data at rest & in transit; proper secrets management; never show stack traces to users; never put API keys in frontend code. 🇮🇷 انتقال یا ذخیره‌ی اطلاعات حساس بدون رمزنگاری مناسب. راه‌حل: HTTPS اجباری با TLS 1.2+ و HSTS؛ هرگز MD5 یا هش بدون salt — فقط bcrypt/Argon2؛ رمزنگاری داده‌های حساس در Rest و Transit؛ مدیریت صحیح کلیدها و اسرار؛ عدم نمایش Stack Trace به کاربر؛ قرارندادن API Key در کد فرانت‌اند ممنوع.

7 — SSRF | جعل درخواست سمت سرور 🇬🇧 Attackers force the server to call internal network addresses — e.g. a profile image-URL field reading http://169.254.169.254/ (AWS metadata). Fix: whitelist allowed domains, block internal & loopback IPs, no automatic redirects. 🇮🇷 مهاجم سرور را وادار می‌کند به آدرس‌های داخلی شبکه درخواست بفرستد — مثلاً فیلد URL عکس پروفایل با http://169.254.169.254/ اطلاعات حساس سرور را می‌خواند. راه‌حل: Whitelist دامنه‌های مجاز، مسدودکردن IPهای داخلی و Loopback، عدم ارسال خودکار Redirectها.

8 — Security Misconfiguration | پیکربندی ناامن 🇬🇧 Debug mode in production, directory listing enabled, default pages & server version banners (e.g. Server: Apache 2.4.49), CORS set to *, unprotected admin panels. Fix: server hardening, remove unneeded services, CORS only for allowed domains, Security Headers. 🇮🇷 حالت Debug در Production، Directory Listing فعال، صفحات پیش‌فرض و اطلاعات نسخه‌ی سرور (مثل Server: Apache 2.4.49)، CORS با تنظیمات باز (*) و پنل‌های مدیریتی بدون محافظت. راه‌حل: Hardening سرور و حذف سرویس‌های غیرضروری، تنظیم CORS فقط برای دامنه‌های مجاز و Security Headers.

9 — Vulnerable Components | کامپوننت‌های آسیب‌پذیر 🇬🇧 Old libraries/frameworks with known vulnerabilities. Fix: regular package updates, review the details, remove unused dependencies. 🇮🇷 استفاده از کتابخانه‌ها و فریم‌ورک‌های قدیمی با آسیب‌پذیری شناخته‌شده. راه‌حل: به‌روزرسانی منظم پکیج‌ها، بررسی جزئیات و حذف وابستگی‌های استفاده‌نشده.

10 — Unsafe File Uploads | آپلود ناامن فایل‌ها 🇬🇧 Malicious uploads such as web shells via extension tricks. Fix: whitelist extensions & MIME types, random filenames stored outside the web root, antivirus scanning, no execute permission — full details in the File Upload card (group 5). 🇮🇷 آپلود فایل مخرب مثل Webshell با تغییر پسوند. راه‌حل: Whitelist پسوندها و MIME Typeها، تغییر نام فایل‌ها و ذخیره خارج از ریشه‌ی وب، اسکن آنتی‌ویروس، حذف دسترسی اجرا — جزئیات کامل در کارت آپلود فایل (گروه ۵).
