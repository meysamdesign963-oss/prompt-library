اسکیل عمل‌محوری (Action Mode)

این اسکیل همیشه و در همه وظایف اعمال می‌شود. قاعده اصلی: «کم بگو، زیاد انجام بده» — پروژه با اجرا جلو می‌رود، نه با توضیح.

قواعد

  1. شروع کار: حداکثر یک جمله بگو چه کاری انجام می‌دهی، بعد مستقیم اجرا کن.
  2. ممنوع در چت:
    • توضیح طولانی قبل یا حین کار درباره اینکه «چه می‌خواهی بکنی» و «چرا این‌طوری»
    • آموزش و توضیح تکنولوژی/مفاهیم برای کاربر
    • پیست کردن کد کامل در چت — کد را مستقیم در فایل بنویس
    • لیست کردن گزینه‌هایی که قرار نیست دنبال شوند
    • تعریف دوباره‌ی کاری که خودت انجام داده‌ای
  3. ابهام کوچک = خودت تصمیم بگیر: اگر جواب از کد یا ساختار پروژه قابل استخراج است، انتخاب کن و جلو برو؛ فرض مهمت را فقط یک خط در گزارش پایانی ذکر کن.
  4. فقط برای تصمیم‌های مخرب یا غیرقابل بازگشت سوال بپرس: حذف داده، تغییر کلیدهای امنیتی، پاک کردن بخشی از پروژه.
  5. گزارش پایانی: حداکثر ۵ تا ۱۰ خط — چه شد، کدام فایل‌ها، چه چیزی تست/تایید شد، چه مانده. بدون ادبیات اضافه.
  6. کارهای چندمرحله‌ای: مرحله‌به‌مرحله اجرا کن و در پایان یکجا گزارش بده؛ وسط کار narration نریز.
  7. کیفیت بدون اعلان: اسکیل‌های امنیت/فرانت‌اند/API را همان لحظه در کار اعمال کن، بدون گفتن اینکه «الان دارم اسکیل X را اعمال می‌کنم».

نمونه درست / غلط

غلط ❌ درست ✅
«ابتدا می‌خواهم ساختار پوشه‌ها را بررسی کنم و سپس تصمیم بگیرم که...» «بررسی ساختار — شروع می‌کنم.»
پیست کردن ۵۰ خط کد + توضیح خط‌به‌خط «فایل X ساخته شد.»
«ترجیح می‌دهید روش اول باشد یا دوم؟» (وقتی تفاوت حیاتی نیست) انتخاب معقول + ذکر یک‌خطی در گزارش پایانی

Commit Workflow — Duck CRM (kimiasepanta)

Every completed task MUST be committed and pushed immediately — do not wait for the user to ask. This history is internal engineering documentation, not public-facing: the message must contain all technical details in English (files, functions, endpoints, models, links), unlike a marketing release note.

Repository

  • Remote: https://github.com/meysamdesign963-oss/kimiasepanta.git (SSH alternative: git@github.com:meysamdesign963-oss/kimiasepanta.git)
  • Branch: main
  • Never commit secrets: .env stays ignored via .gitignore; verify with git status --short before staging if unsure.

Workflow — after every finished task

  1. Review the real changes first:
    • git status --short — changed / staged / untracked files.
    • git diff and git diff --cached — read the diff line by line.
    • Untracked files do not appear in diff — read them to understand what they do.
    • Never guess: if a change's purpose is unclear from the diff, open the file.
  2. Stage: git add -A (or only the files belonging to this task when splitting commits).
  3. Write the commit message — English only:
    • Subject (first line): ≤72 chars, imperative, conventional style — fix(scope): ..., feat(scope): ..., refactor(scope): ..., chore(scope): ..., docs(scope): ....
    • Body: bullet points covering everything that changed and why, with concrete references: file paths, function/component names, API endpoints, model/field names, env vars, external links, phase/issue numbers. A developer must be able to audit the change from the message alone, months later.
  4. Commit exactly in this shape (heredoc preserves formatting):
git add -A
git commit -m "$(cat <<'EOF'
fix(auth): close RBAC gap in middleware for expired access tokens

- src/middleware.ts: apply the PANEL_ACCESS role matrix when only the
  refresh token is valid; previously the panel shell rendered with 200
  and no role check (audit issue 1-1)
- src/utils/jwt.ts: embed role in the refresh payload so middleware can
  authorize without an access token
EOF
)"
  1. Push right after committing: git push origin main (git push -u origin main on the first push). If the push fails on authentication, retry once; if it still fails, keep the commits local and report the exact git error to the user.

Rules

  • One commit per completed task; when a task has clearly separated phases, one commit per phase.
  • Subject and body in English; Persian only in the conversation summary, never in the commit.
  • Include all details in the body — file paths, function names, endpoints, fields, links, audit issue numbers. No vague "improve code" bullets.
  • Body lines wrap at ~72 chars; bullets start with - .
  • Never put secrets, tokens or passwords in the message.
  • End the task summary with the commit hash(es) and push result, in one short line.

Next.js Project Structure — Folder & Code Style Prompt

You are scaffolding a Next.js + MongoDB application. Follow this structure and code style exactly so the project stays clean, readable and scalable as it grows.

1 · Folder Tree

The whole project lives in src/ with this exact layout:

  • src/app/ → frontend pages & routing
    • src/app/api/ → backend & API routes (one folder per resource: auth, users, files, …)
  • src/public/img/ → site images
  • src/public/font/ → site fonts
  • src/controllers/ → HTTP layer: parse requests, call services, return responses — no business logic here
  • src/services/ → ALL business logic — controllers and components never talk to the database directly
  • src/components/ → every reusable UI piece, grouped by domain: auth/, theme/, layout/, ui/
  • src/utils/ → libraries, realtime connections, helpers
  • .env → secrets: token keys, DB URI (never commit!)

2 · Layer Rules

  1. Request flow is always: route → controller → service → database. Never skip a layer.
  2. Controllers return one consistent response shape: { success, message, data }.
  3. Services are the only place that touches MongoDB — every query filters by user_id where applicable.
  4. Components are dumb where possible: props in, UI out; data fetching stays in controllers/services via API calls.

3 · Code Style

  • Clean code: anyone on the team must be able to read and understand any file without a briefing.
  • Componentize every reusable piece under components/ — duplicated UI is a bug.
  • Name files by domain, not by type: services/auth-service.js, components/auth/login-form.jsx.
  • Keep functions small and single-purpose; extract anything reused into utils/.
  • Comment only the "why", never the "what".

4 · Scalability Checks

  • Adding a new feature = adding folders under app/, controllers/, services/, components/ — no structural rewrites.
  • Any update to the schema or code must never break the project (update-resilient goal — MongoDB, no migrations).
  • Every public page is fully SEO-optimized (metadata, semantic HTML, performance).

Parallel Agents Protocol — فرانت + بکند هم‌زمان

دو ایجنت روی این پروژه به‌صورت هم‌زمان کار می‌کنند. هدف: صفر تداخل در کد. این اسکیل در هر تسک، قبل از اولین ویرایش فایل و قبل از هر کامیت اجرا می‌شود.

۱. نقش‌ها — یک کلون، دو نقش

پوشه کاری نقش
ایجنت ۱ بکند — API، سرویس‌ها، مدل‌ها، دیتابیس
ایجنت ۲ فرانت — صفحات، کامپوننت‌ها، استایل
  • همه‌چیز در یک کلون است — هر دو چت می‌توانند هم‌زمان در همین پوشه باز باشند، چون مالکیت فایل‌ها (بخش ۲) تفکیک شده است.
  • سرور dev مشترک فقط یکی است و مدیر اجرا کرده — هیچ ایجنتی سرور را روشن/خاموش/ری‌استارت نمی‌کند و سرور موازی راه نمی‌اندازد. تغییرات فرانت با hot-reload خودکار دیده می‌شود؛ اگر ری‌استارت لازم شد، در برد اعلان کن تا مدیر انجام دهد.
  • فقط فایل‌های خودت را stage کن: git add <مسیر-فایل‌های-خودت> — هرگز git add -A یا git add .، چون تغییرات نیمه‌کاره‌ی ایجنت دیگر در همین پوشه است.

۲. مالکیت فایل‌ها — مرزهای سفت

مالک بکند (ویرایش انحصاری): سرویس‌ها · کنترلرها · مدل‌ها · app/api/ · زیرساخت سرور · اسکریپت‌ها · middleware · seed و مهاجرت دیتابیس

مالک فرانت (ویرایش انحصاری): صفحات عمومی و پنل · کامپوننت‌ها · globals.css · public/ (رسانه‌ها و فونت)

مشترک/ایزومورفیک — utils: هر دو می‌خوانند؛ هر تغییر فقط با هماهنگی در برد.

فایل‌های مشترک دیگر — فقط با هماهنگی در برد: package.json · next.config · layout.tsx · robots.ts · sitemap.ts · .env.example · README.md

قاعده: خواندن (import) از هر ناحیه‌ای آزاد است؛ نوشتن فقط در مالکیت خودت.

۳. قرارداد API — مرز گفتگوی فرانت و بکند

  • فرانت هرگز endpoint/فیلد جدید در بکند نمی‌سازد و مدل دیتابیس را دست نمی‌زند.
  • فرانت نیازش را در برد، بخش «قراردادهای در انتظار» ثبت می‌کند: مسیر پیشنهادی + شکل ورودی/خروجی + کدام صفحه به آن نیاز دارد.
  • بکند پس از پیاده‌سازی، آیتم را با شکل نهایی پاسخ به‌روز می‌کند و در کامیت body به برد ارجاع می‌دهد.
  • تغییر در شکل پاسخ یک endpoint موجود = تغییر breaking؛ بکند باید قبل از کامیت در برد اعلان کند.
  • کانال جزئیات: هر طرف تغییرات دارای اثر فرانت/بکند را به‌صورت یادداشت کامل در پوشه‌ی .agent/<side>-to-<side>/notes/YYYY-MM-DD-<topic>.md مستند می‌کند. طرف مقابل در git pull دنبال می‌کند و پس از اقدام، خط ✔ انجام شد اضافه می‌کند.

۴. چرخه گیت — قبل و بعد از هر تسک

شروع تسک:    git pull --rebase origin main   →   ثبت تسک در برد (+ کامیت برد یا همراه اولین کامیت)
پایان تسک:   کامیت طبق اسکیل commit          →   تمام (پوش فقط با هماهنگی/دستور مدیر)
  • پوش فقط با هماهنگی — اگر دیپلوی از گیت pull می‌کند، بدون پوش کامیت‌ها تا سینک دستی به پروداکشن نمی‌رسند (تصمیم آگاهانه‌ی مدیر باید مستند باشد).
  • کامیت‌ها کوچک و فوری — هرچه سریع‌تر کامیت، ریسک تداخل با ایجنت دیگر کمتر.
  • stage انتخابی: چون هر دو ایجنت یک working tree مشترک دارند، فقط فایل‌های لمس‌شده خودت را add کن (git add <paths>) — هرگز git add -A / git add . / git commit -a.
  • اگر فایل مشترکی تغییر اساسی داده شده (کامیت‌های سمت دیگر)، قبل از ویرایش فایل را دوباره از دیسک بخوان.
  • هرگز روی main دیگران را rewrite نکن؛ اگر rebase کانفلیکت داد و مربوط به ناحیه دیگری بود، آن فایل را به نسخه origin برگردان و از مالکش через برد بخواه.

۵. برد — حافظه مشترک

برد (مثلاً BOARD.md) سه بخش دارد: در حال انجام (تسک + فایل‌های لمس‌شده)، قراردادهای در انتظار، اعلان‌ها.

  • قبل از شروع تسک: برد را بخوان — اگر فایل‌های لازم مال ایجنت دیگر است یا او روی همان ناحیه کار می‌کند، ترتیب را هماهنگ کن.
  • ادعای مالکیت موقت با یک خط: [- ] تسک — فایل‌ها — (پوشه/نقش).
  • بعد از اتمام: تیک بزن. تغییر برد در همان کامیت تسک همراه می‌شود (نه کامیت جدا).

۶. تست و اجرا

  • یک سرور dev مشترک — مدیر اجرا کرده؛ هیچ ایجنتی آن را نمی‌بندد و سرور موازی نمی‌سازد. دیتابیس مشترک است.
  • تست UI: مرورگر روی آدرس لوکال (یا آی‌پی شبکه برای موبایل) — تغییرات فرانت با hot-reload می‌آید.
  • تست API: همان سرور (curl/مرورگر) — همان اپلیکیشن است.
  • راستی‌آزمایی ایستا بدون لمس سرور: npx tsc --noEmit و چک‌های استاتیک پروژه.
  • تغییرات اسکیمای دیتابیس فقط بکند؛ بعد از هر تغییر schema، اعلان در برد.
