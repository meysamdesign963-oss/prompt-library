Parallel Agents Protocol

(دسته: گردش کار) قرارداد هماهنگی دو ایجنت که هم‌زمان روی یک پروژه کار می‌کنند (یک کلون، دو نقش) — مالکیت فایل‌ها، استیج انتخابی، قرارداد API بین فرانت و بکند، برد هماهنگی و چرخه گیت. قبل از اولین ویرایش فایل و قبل از هر کامیت، در هر تسکی که ستاپ دو-ایجنتی فعال است اجرا شود.

Parallel Agents Protocol — فرانت + بکند هم‌زمان

دو ایجنت روی این پروژه به‌صورت هم‌زمان کار می‌کنند. هدف: صفر تداخل در کد. این اسکیل در هر تسک، قبل از اولین ویرایش فایل و قبل از هر کامیت اجرا می‌شود.

۱. نقش‌ها — یک کلون، دو نقش

پوشه کاری نقش
ایجنت ۱ بکند — API، سرویس‌ها، مدل‌ها، دیتابیس
ایجنت ۲ فرانت — صفحات، کامپوننت‌ها، استایل
  • همه‌چیز در یک کلون است — هر دو چت می‌توانند هم‌زمان در همین پوشه باز باشند، چون مالکیت فایل‌ها (بخش ۲) تفکیک شده است.
  • سرور dev مشترک فقط یکی است و مدیر اجرا کرده — هیچ ایجنتی سرور را روشن/خاموش/ری‌استارت نمی‌کند و سرور موازی راه نمی‌اندازد. تغییرات فرانت با hot-reload خودکار دیده می‌شود؛ اگر ری‌استارت لازم شد، در برد اعلان کن تا مدیر انجام دهد.
  • فقط فایل‌های خودت را stage کن: git add <مسیر-فایل‌های-خودت> — هرگز git add -A یا git add .، چون تغییرات نیمه‌کاره‌ی ایجنت دیگر در همین پوشه است.

۲. مالکیت فایل‌ها — مرزهای سفت

مالک بکند (ویرایش انحصاری): سرویس‌ها · کنترلرها · مدل‌ها · app/api/ · زیرساخت سرور · اسکریپت‌ها · middleware · seed و مهاجرت دیتابیس

مالک فرانت (ویرایش انحصاری): صفحات عمومی و پنل · کامپوننت‌ها · globals.css · public/ (رسانه‌ها و فونت)

مشترک/ایزومورفیک — utils: هر دو می‌خوانند؛ هر تغییر فقط با هماهنگی در برد.

فایل‌های مشترک دیگر — فقط با هماهنگی در برد: package.json · next.config · layout.tsx · robots.ts · sitemap.ts · .env.example · README.md

قاعده: خواندن (import) از هر ناحیه‌ای آزاد است؛ نوشتن فقط در مالکیت خودت.

۳. قرارداد API — مرز گفتگوی فرانت و بکند

  • فرانت هرگز endpoint/فیلد جدید در بکند نمی‌سازد و مدل دیتابیس را دست نمی‌زند.
  • فرانت نیازش را در برد، بخش «قراردادهای در انتظار» ثبت می‌کند: مسیر پیشنهادی + شکل ورودی/خروجی + کدام صفحه به آن نیاز دارد.
  • بکند پس از پیاده‌سازی، آیتم را با شکل نهایی پاسخ به‌روز می‌کند و در کامیت body به برد ارجاع می‌دهد.
  • تغییر در شکل پاسخ یک endpoint موجود = تغییر breaking؛ بکند باید قبل از کامیت در برد اعلان کند.
  • کانال جزئیات: هر طرف تغییرات دارای اثر فرانت/بکند را به‌صورت یادداشت کامل در پوشه‌ی .agent/<side>-to-<side>/notes/YYYY-MM-DD-<topic>.md مستند می‌کند. طرف مقابل در git pull دنبال می‌کند و پس از اقدام، خط ✔ انجام شد اضافه می‌کند.

۴. چرخه گیت — قبل و بعد از هر تسک

شروع تسک:    git pull --rebase origin main   →   ثبت تسک در برد (+ کامیت برد یا همراه اولین کامیت)
پایان تسک:   کامیت طبق اسکیل commit          →   تمام (پوش فقط با هماهنگی/دستور مدیر)
  • پوش فقط با هماهنگی — اگر دیپلوی از گیت pull می‌کند، بدون پوش کامیت‌ها تا سینک دستی به پروداکشن نمی‌رسند (تصمیم آگاهانه‌ی مدیر باید مستند باشد).
  • کامیت‌ها کوچک و فوری — هرچه سریع‌تر کامیت، ریسک تداخل با ایجنت دیگر کمتر.
  • stage انتخابی: چون هر دو ایجنت یک working tree مشترک دارند، فقط فایل‌های لمس‌شده خودت را add کن (git add <paths>) — هرگز git add -A / git add . / git commit -a.
  • اگر فایل مشترکی تغییر اساسی داده شده (کامیت‌های سمت دیگر)، قبل از ویرایش فایل را دوباره از دیسک بخوان.
  • هرگز روی main دیگران را rewrite نکن؛ اگر rebase کانفلیکت داد و مربوط به ناحیه دیگری بود، آن فایل را به نسخه origin برگردان و از مالکش через برد بخواه.

۵. برد — حافظه مشترک

برد (مثلاً BOARD.md) سه بخش دارد: در حال انجام (تسک + فایل‌های لمس‌شده)، قراردادهای در انتظار، اعلان‌ها.

  • قبل از شروع تسک: برد را بخوان — اگر فایل‌های لازم مال ایجنت دیگر است یا او روی همان ناحیه کار می‌کند، ترتیب را هماهنگ کن.
  • ادعای مالکیت موقت با یک خط: [- ] تسک — فایل‌ها — (پوشه/نقش).
  • بعد از اتمام: تیک بزن. تغییر برد در همان کامیت تسک همراه می‌شود (نه کامیت جدا).

۶. تست و اجرا

  • یک سرور dev مشترک — مدیر اجرا کرده؛ هیچ ایجنتی آن را نمی‌بندد و سرور موازی نمی‌سازد. دیتابیس مشترک است.
  • تست UI: مرورگر روی آدرس لوکال (یا آی‌پی شبکه برای موبایل) — تغییرات فرانت با hot-reload می‌آید.
  • تست API: همان سرور (curl/مرورگر) — همان اپلیکیشن است.
  • راستی‌آزمایی ایستا بدون لمس سرور: npx tsc --noEmit و چک‌های استاتیک پروژه.
  • تغییرات اسکیمای دیتابیس فقط بکند؛ بعد از هر تغییر schema، اعلان در برد.
